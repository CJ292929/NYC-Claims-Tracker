# LEGACY — this directory does not describe the production database

The `*.sql` migrations, `meta/` snapshots, and `relations.ts` under `drizzle/` were
generated by `drizzle-kit` for an early **MySQL/TiDB** version of this app
(`dialect: "mysql"` in `drizzle.config.ts`, `DATABASE_URL` connection string, `int`
auto-increment primary keys). `drizzle/schema.ts` no longer contains Drizzle table
definitions — it's now a hand-maintained TypeScript mirror of the Postgres schema
(see below), kept at this path only because `server/db.ts` imports app types from it.

The app was migrated to **Supabase PostgreSQL** (UUID primary keys, snake_case
columns, `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`). None of the code paths used
in production talk to MySQL — `server/db.ts` and `server/routers.ts` only use the
Supabase client (`server/supabase.ts`). The last migration in this directory
(`0003_cool_morlocks.sql`) even `DROP TABLE`s everything it created, confirming this
migration history is dead and was never carried forward.

**Do not run `pnpm db:push` (`drizzle-kit generate && drizzle-kit migrate`) against
production.** It targets `DATABASE_URL` (MySQL), which is not the database this app
reads from or writes to.

## What's actually authoritative

- **Schema (SQL):** [`references/local-setup-schema.sql`](../references/local-setup-schema.sql)
  — the canonical Postgres schema snapshot. Apply changes by hand in the Supabase
  SQL Editor and update this file to match.
- **Types (TypeScript):** `drizzle/schema.ts` (kept for its camelCase app types and
  import path used by `server/db.ts`) and `server/supabase.types.ts`. Both are
  hand-maintained mirrors of the SQL above, not generated — keep them in sync
  manually when the schema changes.

`drizzle-orm` / `drizzle-kit` remain in `package.json` only because `drizzle/schema.ts`
re-exports plain TypeScript types under that path; no ORM query builder or migration
runner is actually exercised at runtime.
